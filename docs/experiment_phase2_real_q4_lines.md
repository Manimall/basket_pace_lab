# Phase 2: реальные четвертные линии → где бук завышает Q4

**Статус:** NEXT / not started
**Предпосылка:** Phase 1 ([[experiment_q4_under_after_3_overs]]) показал, что против прокси `/4` виден только артефакт базовой просадки Q4; настоящую гипотезу «бук завышает Q4» на прокси проверить нельзя. Калиброванный прогон нашёл единственный рычаг — **блоуаут** (margin перед Q4 ≥ 20 → ~60% ТМ против пре-матч линии), но живой бук отрыв видит и линию двигает.
**Цель:** мерить edge против **настоящих** четвертных линий, а не против доли от матчевого тотала.

---

## 1. Главный вопрос и почему он про ЖИВЫЕ линии

Гипотеза «3 четверти ТБ → Q4 ТМ» и «блоуаут → Q4 ТМ» — это **live-ставки**: решение принимается в начале Q4, зная счёт и что было в Q1–Q3. Значит нужна **линия Q4, как её вешал бук на старте Q4** (live), а не пре-матч.

Отсюда два трека сбора (разной сложности и ценности):

| Трек | Что собираем | Отвечает на вопрос | Сложность |
|---|---|---|---|
| **A. Backfill пре-матч** | пре-матчевые четвертные тоталы (если провайдер отдаёт историю) | «завышена ли СТАТИЧЕСКАЯ Q4-линия против реализованной Q4» | средняя |
| **B. Prospective live** | снапшот live Q4-тотала на старте Q4, по ходу сезона | «завышает ли бук Q4 LIVE после 3 четвертей / при блоуауте» — **та самая гипотеза** | высокая, только вперёд |

Честно: трек B **нельзя забэкфиллить** — исторических live-снапшотов Q4-линии у Flashscore нет. Его надо запускать **на будущее** и накапливать за сезон. Трек A — дешевле, но отвечает на более слабый вопрос.

## 2. Схема БД (что добавить)

По аналогии с уже существующими `Match.total_line`, `first_half_line`, `second_half_line` — добавить четвертные:

```
-- migrations/003_add_quarter_lines.sql
ALTER TABLE matches
  ADD COLUMN q1_line       double precision,   -- пре-матч Q1 тотал (трек A)
  ADD COLUMN q2_line       double precision,
  ADD COLUMN q3_line       double precision,
  ADD COLUMN q4_line       double precision,
  ADD COLUMN q4_line_live  double precision,   -- live Q4 тотал на старте Q4 (трек B)
  ADD COLUMN q4_line_live_captured_at timestamptz;
```

Плюс в `src/database/models.py` — соответствующие `Mapped[Optional[float]]` поля в `Match`.

## 3. Трек A — backfill пре-матч четвертных тоталов

- **Источник:** секция odds у провайдера (Flashscore/собранные odds). Проверить в `src/data_collection/flashscore_enricher*.py`, отдаёт ли страница матча Over/Under с селектором периода (Quarter). Многие книги вешают пре-матч Q1/Q4 тоталы.
- **Готча (из памяти проекта):** `period=game needs odds` — четвертные odds могут лежать только там, где вообще есть коэффы; сверить покрытие.
- **Тест:** `blind Q4 ТМ` против `q4_line` (не против `/4`!). Если `mean(realized_q4 − q4_line) < 0` систематически и hit-rate ТМ > 52.6% при 1.90 — статический эдж есть.

## 4. Трек B — prospective live-снапшот (главный)

- **Что:** для каждого CBA-матча по ходу сезона в момент «конец Q3 / старт Q4» дёрнуть live Q4-тотал и записать в `q4_line_live` (+ `captured_at`).
- **Где хукать:** live-поллер поверх `mass_scheduler` / отдельный крон, который по расписанию идёт по идущим CBA-матчам в статусе, где сыграно 3 четверти, и снимает odds Q4.
- **Данные накапливаются вперёд** — за сезон соберётся выборка для проверки:
  1. `blind Q4 ТМ` против `q4_line_live` (базовый: завышает ли бук Q4 live вообще).
  2. **`Q4 ТМ | margin перед Q4 ≥ 18–20`** против `q4_line_live` — проверка блоуаут-сушки против ЖИВОЙ линии (главный кандидат из Phase 1).
  3. `Q4 ТМ | 3 ТБ` против `q4_line_live` — добить исходную гипотезу на честной линии.

## 5. Метрики (для обоих треков)

Переиспользовать `scripts/test_4q_pattern.py`, заменив прокси-линию на реальную:
- hit-rate ТМ, ROI при `settings.evaluation.odds`, bootstrap CI95.
- **base-rate контраст** (эдж = прирост над безусловным ТМ, как в Phase 1 — не голый win rate).
- разбивка по margin-корзинам (0–10 / 10–18 / 18+).

## 6. Готчи

- **Live Q4-линия не бэкфиллится** — трек B только вперёд, начинать сбор ASAP, чтобы набрать n за сезон.
- `period=game needs odds` (покрытие четвертных odds).
- Numeric `external_id` фильтр лиги.
- OT: Q4 regulation-only (`q4_includes_ot_points=False`).
- Блоуаут-эдж почти наверняка **частично съеден живой линией** (бук видит отрыв) — именно это трек B и измеряет: сколько РЕАЛЬНО остаётся.
